# BizNext Connectors — §56: 1С Connector (демо-режим) и контракт реального подключения

> Как BizNext получает данные учётной системы предприятия, не открывая её в интернет и не давая
> AI прямого доступа. Первый коннектор — 1С; тот же путь подходит для MySQL, MS SQL, Excel,
> Google Sheets и REST API.

---

## 1. Идея в одном абзаце

Агент **никогда не ходит в 1С**. Внутри сети предприятия ставится **BizNext Connector** — небольшой
сервис, который под пользователем 1С с правами только на чтение забирает разрешённые данные и
приводит их к **универсальным сущностям** (канонический контракт). Затем он сам, исходящим HTTPS,
отправляет их в BizNext. BizNext хранит канонические таблицы, **стандартные метрики** считаются
только по ним, агент читает только их.

```text
┌──────────────────── Предприятие ────────────────────┐
│                                                     │
│   1С:Предприятие ── OData (GET, read-only user) ──┐ │
│                                                   ▼ │
│                              BizNext Connector       │
│                              маппинг → контракт      │
│                              только нужные поля      │
└──────────────────────────────────┬──────────────────┘
                                   │ исходящий HTTPS, токен источника
                                   ▼
        BizNext ingest API → канонические таблицы (схема источника)
                                   │
                         BizNext Semantic Layer (стандартные метрики)
                                   │
                              BizNext Agent
```

Что говорить IT-специалисту предприятия:
«Мы не даём AI доступ к вашей 1С. Устанавливаем read-only коннектор, который передаёт только
необходимые данные. Входящие порты открывать не нужно».

## 2. Слои и где они в коде

| Слой | Что делает | Где |
|---|---|---|
| Канонический контракт | Универсальные сущности, типы, ключи, режимы загрузки | `contracts/canonical/v1.yaml` |
| Адаптер 1С | OData-клиент (только GET) + декларативный маппинг 1С → контракт | `connector/biznext_connector/onec/`, `connector/mappings/1c_erp_demo.yaml` |
| Интерфейс адаптера | Общий протокол для будущих источников | `connector/biznext_connector/adapters.py` (`SourceAdapter`) |
| Синхронизация | План загрузок: полная раз в сутки, инкрементальная каждые N минут | `connector/biznext_connector/sync.py` |
| Ingest API | Токен → источник, проверка записей по контракту, staging, атомарная замена | `backend/app/api/ingest.py`, `backend/app/ingest/` |
| Хранилище | Схема источника (`onec_demo`) + служебная схема `ingest` | `database/seed/migrate.py` (DDL из контракта) |
| Реестр источников | Какие источники видит агент и как данные приходят | `semantic/sources.yaml` |
| Стандартные метрики | Метрики, дашборд, инсайты и вопросы поверх контракта | `semantic/packs/standard/*.yaml` |
| Контекст предприятия | Бизнес-глоссарий конкретной компании | `semantic/onec_demo/business_context.yaml` |
| Демо-режим 1С | Эмулятор публикации OData над выгрузкой инфобазы | `onec_demo/`, `database/seed/onec_export.py` |

Агент (`backend/app/agent/`) для 1С **не изменялся**: он получает другой коннектор к данным
(схема `onec_demo`), другой семантический слой и тот же набор инструментов. Это и есть проверка
абстракции источника данных.

## 3. Этап 1 — контракт: универсальные сущности

`contracts/canonical/v1.yaml`, версия `1.0`.

| Сущность | Вид | Ключ | Загрузка | Основные поля |
|---|---|---|---|---|
| `products` | справочник | `id` | replace_all | name, sku, item_type (goods/material/service), category, unit |
| `customers` | справочник | `id` | replace_all | name, segment, region, macro_region, manager, tax_id (sensitive) |
| `suppliers` | справочник | `id` | replace_all | name, region, supplier_type, tax_id (sensitive) |
| `warehouses` | справочник | `id` | replace_all | name, region, warehouse_type |
| `employees` | справочник, необязательная | `id` | replace_all | name, department, position, hired_at, terminated_at — **без окладов** |
| `sales` | строки документов | `id` | replace_window по `date` | operation (sale/return), customer_id, product_id, quantity, amount (без НДС), vat_amount, cost_amount, due_date |
| `purchases` | строки документов | `id` | replace_window по `date` | supplier_id, product_id, quantity, amount, vat_amount |
| `production` | строки документов, необязательная | `id` | replace_window по `date` | work_center, product_id, quantity, planned_quantity, defect_quantity |
| `payments` | строки документов | `id` | replace_window по `date` | direction, counterparty_id, settlement_document_id, amount (с НДС) |
| `costs` | строки документов | `id` | replace_window по `date` | cost_item, department, amount |
| `write_offs` | строки документов | `id` | replace_window по `date` | product_id, warehouse_id, quantity, reason, cost_amount |
| `inventory` | срез на дату | `snapshot_date, warehouse_id, product_id` | replace_window по `snapshot_date` | quantity, reorder_point |
| `receivables` | срез на дату | `snapshot_date, document_id` | replace_window по `snapshot_date` | customer_id, due_date, amount_due (с НДС) |

Правила:
- все идентификаторы — строки (у 1С — GUID ссылки, у SQL-источника — ключ, приведённый к строке);
- `replace_all` — справочник целиком заменяется; `replace_window` — всё в окне дат `[from, to)`
  удаляется и вставляется заново, поэтому **распроведённые и удалённые в 1С документы исчезают**;
- поле, которого нет в контракте, отклоняется целиком: лишние данные не могут «просочиться»;
- контракт версионируется; новые необязательные поля добавляются без поломки коннекторов
  (`migrate` добавит колонки), несовместимые изменения — только новая версия `v2`.

### Стандартные метрики (`semantic/packs/standard/metrics.yaml`)

| Метрика | Ключ | Определение |
|---|---|---|
| Выручка | `revenue` | Σ amount строк `sales` с operation = sale, без НДС |
| Себестоимость | `cogs` | Σ cost_amount продаж |
| Прибыль | `gross_profit`, `operating_profit` | выручка − себестоимость; − расходы − списания |
| Маржа | `gross_margin_pct`, `operating_margin_pct` | прибыль / выручка, % |
| Объём производства | `production_volume` | Σ quantity выпуска |
| Остатки | `inventory_units`, `inventory_below_reorder` | остаток на последний срез периода; позиции ниже норматива |
| Продажи | `units_sold`, `orders_count`, `average_order_value`, `active_customers`, `returns_amount`, `net_revenue` | |
| Закупки | `purchase_amount` | Σ amount поступлений, без НДС |
| Задолженность | `receivables_total`, `overdue_receivables`, `payments_received` | долг клиентов с НДС на срез; просроченный |
| Оборачиваемость | `inventory_turnover_days`, `receivables_turnover_days` | остаток / продажи × дней периода; долг / продажи с НДС × дней |
| Списания | `write_off_cost` | Σ cost_amount списаний |

Для оборачиваемости в формулы добавлена переменная `period_days` (дней в периоде или в бакете
временного ряда) — числа по-прежнему считает Python, а не LLM.

## 4. Этап 2 — адаптер 1С

### 4.1 Протокол

Стандартный интерфейс OData 1С (`/<база>/odata/standard.odata/`), JSON. Используется только:
- `GET <Объект>?$filter=…&$select=…&$top=…&$skip=…&$orderby=…` — справочники, документы с
  табличными частями, записи регистров;
- `GET <Регистр>/Balance(Period=datetime'…')` — виртуальная таблица остатков;
- `GET <Объект>/$count` и корень сервиса — для проверки `check`.

`ODataClient` не содержит методов записи. Прямое подключение к SQL-базе 1С не используется:
оно нарушает лицензию и ломается при обновлении конфигурации.

### 4.2 Маппинг вместо кода

`connector/mappings/1c_erp_demo.yaml` описывает для каждой канонической сущности объект 1С,
фильтр (`Posted eq true and DeletionMark eq false`), дату, табличную часть и выражения полей:
реквизит шапки или строки, поиск в справочнике (с цепочкой `then`, например регион → макрорегион),
`coalesce`, арифметику (`line.Сумма - line.СуммаНДС`), перекодировку значений (`Товар → goods`),
обогащение из регистра (себестоимость из `ВыручкаИСебестоимостьПродаж` с распределением по
количеству), дополнение срезов (позиции с нормативом запаса, но без остатка → 0).

Коннектор строит `$select` **только из реквизитов маппинга**. Оклады сотрудников в маппинг не
входят и не запрашиваются; `tax_id` (БИН/ИИН) исключён политикой `CONNECTOR_EXCLUDE_FIELDS` и тоже
не запрашивается. Это проверяется тестом по реальным URL запросов.

Новая конфигурация 1С клиента (БП 3.0, УТ 11, УНФ, доработанная ERP) = копия маппинга с другими
именами объектов и реквизитов. Агент, метрики и BizNext не меняются.

### 4.3 Синхронизация

| Режим | Когда | Что загружается |
|---|---|---|
| полная (`full`) | первая синхронизация и раз в сутки после `FULL_SYNC_TIME` | справочники; документы за `SYNC_HISTORY_MONTHS` (14) месяцев, помесячно; остатки на конец каждого месяца + ежедневно за 62 дня; задолженность на конец месяцев + сегодня |
| инкрементальная | каждые `SYNC_INTERVAL_MINUTES` (30) | справочники; документы за последние `SYNC_LOOKBACK_DAYS` (35) дней; остатки за вчера и сегодня; задолженность на сегодня |

Протокол ingest API (`/api/ingest/v1`, заголовок `Authorization: Bearer <токен источника>`):

```text
GET  /state                         → последняя успешная полная/любая синхронизация
POST /runs {kind, connector}        → run_id   (connector — описание без секретов: конфигурация, объекты, исключённые поля)
POST /loads {run_id, entity, mode, window_from, window_to} → load_id
POST /loads/{id}/chunks {seq, records[]}   (gzip; повтор seq заменяет пакет — идемпотентно)
POST /loads/{id}/commit {expected_records} → {received, inserted, deleted}
POST /runs/{id}/finish {status, stats, error}
```

`commit` в одной транзакции: блокировка сущности, сверка количества, удаление окна, вставка из
staging с дедупликацией по ключу, `ANALYZE`. Ошибка одной сущности не мешает остальным, частично
загруженные данные не видны агенту.

## 5. Безопасность

| Угроза | Защита |
|---|---|
| 1С доступна из интернета | Нет: коннектор внутри сети предприятия делает только исходящие запросы; входящие порты не открываются. В демо это сеть Docker `enterprise` (`internal: true`), у backend к ней нет маршрута — проверяется интеграционным тестом |
| AI меняет данные в 1С | Пользователь публикации 1С с ролью только чтения; клиент коннектора умеет только GET; эмулятор отвечает 403 на любые изменения |
| Лишние данные уходят из предприятия | Передаются только поля маппинга; чувствительные поля исключаются политикой до запроса; контракт отклоняет неизвестные поля |
| Чужой коннектор пишет данные | Токен привязан к одному источнику; `INGEST_TOKENS=source_id:token` |
| Коннектор портит другие данные | Роль `INGEST_DB_USER` пишет только в схемы канонических источников и `ingest`; к `demo` и `app` доступа нет |
| Агент читает staging или пишет в канонические таблицы | Роль агента: только SELECT по схеме источника, `ingest` недоступна, read-only транзакции |
| Секреты в логах | Коннектор и backend маскируют токены и пароли; в статусе коннектора — только хост и путь публикации |

Для промышленного внедрения дополнительно: HTTPS с проверкой сертификата (`VERIFY_TLS=1`),
ротация токена, IP-allowlist BizNext, отдельная роль БД агента на каждого клиента (или отдельная БД),
установка коннектора как службы Windows/Linux рядом с сервером 1С.

## 6. Демо-режим

Сервисы `docker compose`:

| Сервис | Сеть | Роль |
|---|---|---|
| `seed` | default | после генерации данных выгружает **тот же бизнес** как инфобазу 1С (SQLite): GUID-ссылки, документы с табличными частями, НДС 12 %, проведение, регистры |
| `onec-demo` | enterprise | эмулятор публикации `standard.odata` над инфобазой; Basic-аутентификация, только чтение |
| `connector` | enterprise + default | BizNext Connector: полная синхронизация при старте, дальше по расписанию |
| `migrate` | default | роль `biznext_ingest`, схема `ingest`, схема `onec_demo` с таблицами из контракта |
| `backend` | default | два источника: `demo_postgres` (прямое чтение) и `onec_demo` (канонические таблицы) |

Так как в «1С» тот же бизнес, стандартные метрики по 1С **обязаны совпасть** с метриками прямого
источника. Это проверяется интеграционным тестом сверки: выручка, себестоимость, прибыль,
расходы, списания, количество продаж и клиентов, возвраты, выпуск, закупки, остатки — за прошлый
месяц и прошлый квартал, а также выручка по категориям.

В UI переключатель источника в шапке меняет дашборд, инсайты, подсказки и новые диалоги.
Страница «Источники данных» показывает схему потока, состояние синхронизации, сущности с объектами
1С и числом записей, меры безопасности.

Команды:

```bash
docker compose up -d --build                                   # всё, включая эмулятор 1С и коннектор
docker compose logs -f connector                               # ход синхронизации
docker compose run --rm connector python -m biznext_connector check          # объекты 1С опубликованы?
docker compose run --rm connector python -m biznext_connector once --full    # принудительная полная загрузка
```

Ограничения демо: эмулятор реализует подмножество OData, достаточное для маппинга; простои линий
и план продаж в «1С» не ведутся — на такие вопросы агент по источнику 1С честно отвечает, что
данных нет.

## 7. Путь к первому production-коннектору

1. **Выбрать одну конфигурацию** у реального клиента (например, 1С:ERP 2.5 или УТ 11.5) и версию платформы.
2. **Публикация OData**: включить состав стандартного интерфейса только для объектов маппинга
   (`УстановитьСоставСтандартногоИнтерфейсаOData`), создать пользователя с ролью только на чтение этих объектов.
3. **Маппинг**: скопировать `1c_erp_demo.yaml`, заменить имена объектов/реквизитов, проверить
   `python -m biznext_connector check` на копии базы.
4. **Сверка с отчётами 1С**: выручка, себестоимость, остатки, задолженность за закрытый месяц должны
   совпасть с «Валовой прибылью», «Ведомостью по товарам», «Расчётами с клиентами». Расхождения —
   правка маппинга, не агента.
5. **Установка**: коннектор как служба на сервере в сети предприятия, `BIZNEXT_URL=https://…`,
   `VERIFY_TLS=1`, отдельный токен источника; источник с `mode: live` в `semantic/sources.yaml`.
6. **Пилот**: 2–4 недели ежедневной синхронизации, контроль ошибок в статусе коннектора, затем вопросы директора.

Для других систем тот же порядок: новый адаптер реализует `SourceAdapter` (MySQL/MS SQL — SQL-запросы
только чтения, Excel/Google Sheets — чтение листов, REST API — HTTP-клиент), маппинг ведёт к тому же
контракту, стандартные метрики и агент переиспользуются без изменений.
