# Задача

Ты — senior full-stack developer + data engineer + AI engineer + product designer.

Нужно самостоятельно спроектировать и собрать **рабочий демонстрационный MVP AI Data Agent**, который в дальнейшем будет использоваться как основа коммерческого B2B-продукта для предприятий.

Рабочее название проекта:

**BizNext Agent**

Идея продукта:

> Руководитель предприятия задаёт вопросы о бизнесе обычным человеческим языком, а AI-агент самостоятельно определяет, какие данные ему нужны, получает их из базы данных, анализирует их и возвращает понятный ответ, таблицы, KPI и графики.

Это НЕ должен быть обычный chatbot с заранее зашитыми ответами.

Главная демонстрационная ценность:

```text
Пользователь
    ↓
Пишет вопрос обычным языком
    ↓
AI Agent понимает задачу
    ↓
Определяет необходимые данные
    ↓
Формирует SQL / вызывает инструменты
    ↓
Получает реальные данные из БД
    ↓
Проверяет результат
    ↓
Анализирует
    ↓
Возвращает понятный ответ
    ↓
При необходимости строит таблицу / график
```

# 7. Архитектура AI Agent

Это ключевая часть проекта.

Не делай:

```text
question
↓
LLM
↓
готовый текст
```

Нужен tool-based агент.

Примерная логика:

```text
User Question
      ↓
Agent
      ↓
Understand Intent
      ↓
Determine Required Data
      ↓
Inspect Schema
      ↓
Generate SQL
      ↓
Validate SQL
      ↓
Execute READ-ONLY SQL
      ↓
Analyze Result
      ↓
Decide Response Type
      ↓
Text / Table / Chart / KPI
      ↓
Final Response
```

### LLM provider abstraction

Архитектуру LLM provider сделай через отдельный abstraction layer.

На первом этапе используй API-модель через environment variables, но не привязывай бизнес-логику агента непосредственно к конкретному провайдеру.

В будущем должна быть возможность заменить модель без переписывания Agent.

```text
Agent (tool loop, бизнес-логика)
      ↓
LLMProvider interface
      ↓
OpenAI / Anthropic / другой провайдер / локальная модель
```

Agent работает только с интерфейсом `LLMProvider`. Конкретный провайдер выбирается через `.env` (см. раздел 21).

# 9. SQL Safety

Это обязательная часть.

Никогда не позволяй LLM напрямую выполнять произвольный SQL без проверки.

Pipeline:

```text
LLM generates SQL
        ↓
SQL Validator
        ↓
Check query type
        ↓
Reject dangerous operations
        ↓
Limit rows
        ↓
Optional timeout
        ↓
Execute
```

Все SQL queries должны быть read-only.

Добавь:

- LIMIT;
- query timeout;
- запрет multiple statements;
- запрет destructive SQL;
- логирование query;
- обработку SQL errors.

Если SQL некорректный:

```text
SQL Error
    ↓
Agent receives error
    ↓
Agent исправляет запрос
    ↓
Retry
```

Ограничь количество retry, например 2–3.

### Read-only на уровне базы данных

Обязательно запрети агенту выполнять SQL от имени обычного PostgreSQL пользователя.

Создай отдельного PostgreSQL пользователя `agent_readonly`, которому предоставлены только SELECT-права на demo schema.

Даже если SQL validator будет обойден, database-level permissions должны физически не позволять INSERT/UPDATE/DELETE/DDL операции.

SQL validator — первый уровень защиты, права в PostgreSQL — второй, и он не зависит ни от LLM, ни от кода приложения.

История запросов и traces хранятся под отдельным пользователем приложения в отдельной schema, к которой у `agent_readonly` доступа нет.

# 10. AI должен уметь анализировать результаты

После получения данных агент НЕ должен просто копировать таблицу пользователю.

Он должен:

1. понять результат;
2. определить ключевые показатели;
3. найти изменения;
4. при необходимости сравнить периоды;
5. выделить важные отклонения;
6. дать краткий вывод.

Например:

```text
Продажи в августе составили 48,2 млн ₸.

Это на 8,4% выше июля.

Основной рост пришёлся на категорию X:
+17,2%.

При этом категория Y снизилась на 9,3%.

Наибольшее снижение наблюдается у ...
```

Все цифры должны приходить из реальных результатов SQL.

**Не выдумывать цифры.**

LLM не должна сама считать финансовые показатели, если это можно сделать SQL/Python. Суммы, разницы, проценты изменения и доли рассчитываются детерминированно, а модель их интерпретирует (см. разделы 17 и 46).

# 17. AI Insights

На Dashboard добавь блок:

### AI Insights

Например:

```text
⚠️ Производительность снизилась на 12%.

📈 Продажи категории X выросли на 18%.

📦 Запасы продукта Y находятся ниже среднего уровня.

💰 Маржинальность выросла на 4,2%.
```

Insights не должны быть полностью автономной генерацией LLM.

Pipeline:

```text
SQL/KPI calculation
       ↓
deterministic metrics
       ↓
LLM interpretation
       ↓
AI Insight
```

То есть сначала SQL/Python действительно рассчитывает показатели, например:

```text
revenue = 48,234,221
growth = -8.4%
```

и только потом LLM формулирует вывод:

> «Выручка снизилась на 8,4%, основное снижение связано с категорией X».

LLM не должна сама считать финансовые показатели, если это можно сделать SQL/Python. Все числа в insight должны совпадать с рассчитанными метриками.

Можно сделать endpoint:

```text
GET /api/insights
```

который анализирует текущие KPI.

# 24. Тесты

Создай базовые automated tests.

Минимально:

### Database

Проверка подключения.

### SQL validator

Проверить:

```text
SELECT → allowed

INSERT → rejected

UPDATE → rejected

DELETE → rejected

DROP → rejected

multiple statements → rejected
```

### Database permissions

Проверить, что под `agent_readonly` INSERT/UPDATE/DELETE/DDL падают с ошибкой прав на уровне PostgreSQL — в обход validator.

### Agent limits

Проверить, что агент останавливается при достижении лимита iterations/tool calls и retries.

# 26. Ошибки

Если агент не знает ответа:

НЕ выдумывать.

Например:

> Я не могу надёжно ответить на этот вопрос на основе доступных данных.

И объяснить:

> В подключённой базе нет информации о ...

Агент никогда не должен делать вывод, если данных недостаточно.

Если вопрос невозможно надёжно ответить на основании доступных данных, он должен явно сообщить об ограничении.

Запрещено додумывать отсутствующие значения.

Если SQL не удался:

> Не удалось получить данные. Попробуйте переформулировать вопрос.

Если LLM недоступна:

> AI service unavailable.

Ошибки должны быть понятными.

# 27. Производительность

Не надо преждевременно оптимизировать.

Но:

- SQL query timeout;
- LIMIT;
- connection pooling;
- индексы на очевидных полях;
- не загружать миллионы строк в LLM;
- агрегировать данные SQL-ом до отправки модели.

Ключевое правило:

**Не отправляй необработанный огромный dataset в LLM, если нужный ответ можно получить SQL aggregation.**

Например вместо:

```text
100 000 sales rows
↓
LLM
```

делай:

```sql
SELECT month, SUM(revenue)
GROUP BY month
```

↓

```text
12 rows
```

↓

LLM.

### Контроль стоимости LLM

Чтобы случайно не получить бесконечные вызовы:

- добавь максимальное количество agent iterations/tool calls на один пользовательский запрос;
- ограничь размер данных, передаваемых LLM (число строк и объём результата SQL в контексте модели);
- все retries должны иметь лимит (SQL-исправления, повторы запросов к LLM provider).

При достижении лимита агент останавливается и честно сообщает пользователю, что не смог завершить анализ, а не зацикливается.

Лимиты задаются через environment variables с разумными значениями по умолчанию.

        ↓

        ↓

        ↓

        ↓

Что входит в этапы:

2. **Database + synthetic data** — schema, seed, индексы, `agent_readonly`, data dictionary, business metrics. Проверка: `docker compose up -d` поднимает БД с данными, `agent_readonly` не может писать.

4. **Tests** — validator, database permissions, agent limits, agent, API. Проверка: тесты проходят.
5. **Frontend** — Dashboard, AI Agent, Data Sources, charts, Show analysis.

Если в процессе видишь неоднозначность — выбирай наиболее разумное решение самостоятельно, исходя из цели: **сделать максимально убедительный demo AI Data Agent для потенциального B2B-клиента.**

# 46. Архитектурные принципы для будущего коммерческого продукта

Даже несмотря на то, что это demo MVP, соблюдай следующие принципы:

1. Business logic не должна быть привязана к demo database.

2. Database connector должен быть абстрагирован таким образом, чтобы в будущем можно было заменить PostgreSQL клиента на другой источник данных.

3. LLM provider должен быть заменяемым через abstraction layer.

4. Agent tools должны быть отдельными модулями.

5. SQL execution должен происходить только через отдельный безопасный слой.

6. Database permissions должны обеспечивать read-only доступ независимо от application-level validation.

7. Не передавай в LLM больше данных, чем необходимо для решения задачи.

8. Сначала выполняй вычисления и агрегации на стороне БД, затем передавай модели компактный результат.

9. Все критические числовые показатели должны вычисляться детерминированно через SQL/Python, а LLM должна интерпретировать результаты.

10. Не хардкодь demo-specific business logic в Agent.

11. Demo data должна быть заменяема без изменения Agent.

12. Все основные компоненты должны иметь понятные интерфейсы, чтобы в будущем можно было добавить:
    - 1C connector
    - MySQL connector
    - MS SQL connector
    - REST API connector
    - Excel connector
    - Google Sheets connector

13. Не создавать микросервисную архитектуру без реальной необходимости.

14. Предпочтение отдавать простой модульной архитектуре одного backend-приложения.

15. Любое решение должно оцениваться по вопросу:
    «Поможет ли это в будущем подключить реальное предприятие?»
